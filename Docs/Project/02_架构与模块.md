# 架构与模块

以下是已确认的框架职责与依赖约定，不表示相关能力已实现；实际能力以源码与模块 README 为准。GameInterface、GameHub、GameSDK 是可迁移到多个项目的底层框架，具体游戏功能仍由项目层承担。

## 职责与代码位置

| 层 | 放置位置 | 职责 |
|---|---|---|
| GameInterface | `Packages/GameInterface/<能力>/` | Hub、SDK 及上层通用框架的底层接口与数据契约；接口可由 Hub、SDK 或具体项目实现 |
| GameHub | `Packages/GameHub/<能力>/` | UI、音效、震动、资源管理、热更新等通用框架能力，以及通用启动流程编排 |
| GameSDK | `Packages/GameSDK/<能力>/` | 第三方登录、广告、支付等服务封装，以及框架所需的第三方能力适配，屏蔽供应商和实现库差异 |
| 项目层 | `Assets/Game/<模块>/` | 具体玩法、业务与数据规则、游戏资源、差异化系统实现，以及项目组合入口和流程策略 |

GameHub 负责资源管理、热更新等通用框架与流程，通过 GameInterface 定义的能力工作；具体第三方资源或热更新方案由 GameSDK 适配封装，上层业务与 Hub 不感知底层采用哪种实现库。

三包不得反向依赖 `Assets/Game` 或具体项目实现；契约不泄露厂商 API、实现库类型或专属配置，也不包含具体游戏数据规则。项目通过实现通用接口、提供配置和资源满足自身差异。目录随实际需求建立，模块资产与代码就近组织；共享渲染配置在 `Assets/Settings/`，场景在 `Assets/Scenes/`。

## 面向接口消费，由组合入口提供实现

上层业务与 GameHub 的通用框架、流程均面向 GameInterface 使用能力。项目组合/启动入口选择并创建框架公开的稳定能力实现或项目业务实现，以接口注册；消费者获取接口后调用。注册实例的作用范围与生命周期责任由组装方案明确。

组合入口可引用框架提供的对外实现完成组装，但不选择或创建厂商适配类型。具体实现库的接入、专属配置与初始化、API 适配由 GameSDK 内部承担；契约不变时，更换底层库不要求上层业务或 Hub 通用框架与流程随之修改。

接口来自已明确的通用需求，不要求先有多个项目或跨包消费者，也不预造所有潜在接口。通用契约可由具体项目实现；概念通用不意味着项目的业务与数据规则实现应下沉到 Hub 或 SDK。注册与获取的具体机制和 API 由对应模块方案确定。

## 程序集与依赖方向

下表是编译依赖约定；上层业务和 Hub 通用框架仍遵循上述接口边界，不能因程序集可引用而直接调用供应商或具体适配类型。

| 运行时程序集 | 依赖 |
|---|---|
| GameInterface | 契约所需的通用基础类型；不反向依赖 Hub、SDK 或项目实现 |
| GameSDK | GameInterface 及第三方能力适配所需的库；不反向依赖 GameHub 或项目实现 |
| GameHub | GameInterface、GameSDK |

GameHub 到 GameSDK 的依赖方向已确定，Hub 与 SDK 均依赖 Interface，禁止形成循环。项目组合入口可引用 Interface 契约、Hub/SDK 的对外实现与项目实现，消费者面向接口。

GameHub、GameSDK 的自有运行时代码各由一个程序集承载，功能按目录和命名空间组织，不按功能逐一拆分 asmdef。GameInterface 保持底层契约边界，其与项目层的程序集数量不由这条约束规定。Editor 与 Tests 和运行时隔离，不因“一个运行时程序集”混入编辑器或测试代码，也不合并第三方程序集。

## 通用编排与项目策略

GameHub 通过 GameInterface 契约编排启动、Loading、热更新、登录等通用流程，并提供扩展点。项目组合入口负责对外实现的选择、实例化注册、项目配置与流程策略；流程顺序和产品行为由项目需求决定，不把具体游戏流程硬编码进 Hub。

实际 API 与用法维护在源码旁 README。模块需求和 Task 按[文档组织规范](06_文档组织规范.md)以职责归组；工程质量与验收要求见[工程标准](05_工程实施与验收标准.md)。

# 架构与模块

本文约束新增代码的归属与公共边界，不表示全部能力已实现。实际文件与环境见[工程现状](02_工程现状.md)。

## 代码放在哪里

| 用途 | 放置位置 | 判断条件 |
|---|---|---|
| 游戏玩法、进度、界面与组合入口 | 新模块用 `Assets/Game/<模块>/`，按需分 Runtime/Editor/Tests | 使用本游戏规则、资源或产品状态 |
| 真正跨包使用的接口与数据契约 | `Packages/GameInterface/<能力>/` | 有明确提供方和消费方，只放契约 |
| 不依赖当前游戏的通用工具 | `Packages/GameHub/<能力>/` | 实际消费者需要共用，能脱离游戏独立验证 |
| 平台或第三方服务接入 | `Packages/GameSDK/<能力>/` | 封装 SDK、平台生命周期和回调，游戏要求由契约输入 |

目录随实际需求创建，已有模块沿用有效布局。资产放对应模块的 `Prefab/`、`Data/` 等用途目录；共享渲染配置在 `Assets/Settings/`，场景在 `Assets/Scenes/`。只有多个实际消费者需要才提取共享资产或通用能力。

## 包与程序集边界

出现真实跨模块复用或独立版本维护需求时，再明确公开 API、所需资产、失败行为与调用方，决定抽包。包应能不引用 `Assets/Game` 而编译并被独立消费者验证；游戏资源仍由消费方持有和传入。交付包含代码、资产与 `.meta`、依赖、接线和测试入口，具体检查见[工程标准](06_工程实施与验收标准.md)。

对新增生产代码采用以下依赖方向；实际已声明依赖以源码和 package.json 为准：

| 依赖方 | 允许依赖 | 边界 |
|---|---|---|
| GameInterface | 契约确需的基础类型 | 不依赖 Hub/SDK、游戏实现或 Editor/Test |
| GameHub | 必要 Interface 契约 | 不依赖游戏实现或 Editor/Test |
| GameSDK | 必要 Interface 契约及对应 SDK | 不依赖游戏实现或 Editor/Test |
| 游戏运行时 | 实际使用的 Interface/Hub/SDK 能力 | 不反向引用 Editor/Test |
| Editor/Test | 所服务的运行时程序集 | 不成为生产运行时依赖 |

Hub 与 SDK 的直接依赖只有真实需求成立时才在所属方案中明确单一方向、具体 API 与独立构建影响；不形成循环。同层游戏模块通过公开契约协作，双向关系由组合入口协调，或提取双方真正共用的契约。

具有独立边界的新模块按需定义 asmdef；已受有效 asmdef/asmref 覆盖时不重复建立。Runtime 与 Editor/Test 分离，测试平台按真实夹具选择。程序集引用与包安装依赖分别明确，不用生成 csproj 代替。

## 模块内部怎样分工

- 规则处理输入和业务状态，表现读取结果并驱动画面与声音。实际状态、资源和最终 Transform/布局属性有明确写入者；表现偏移不累计污染玩法基础状态。
- 多宿主可以共享业务能力或资产，视图实例状态与释放责任分别归属。可见、正式提交、挂起与释放含义不同时分别处理，预览不触发仅应在提交时发生的副作用。
- 对外说明初始化、可调用/就绪条件、关闭和失败行为；只暴露消费方需要的稳定契约，外部调用方不感知内部实现变体。
- 不同业务只提取已确认相同的机制，保留各自参数和完成语义。直接调用足够时不用事件；真实订阅或异步关系再定义相应边界。

实际 API 与用法维护在源码旁 README。目标需求和单次实施按[文档组织规范](07_文档组织规范.md)归入同一模块；生命周期、接入与迁移的具体动作见[工程标准](06_工程实施与验收标准.md)。

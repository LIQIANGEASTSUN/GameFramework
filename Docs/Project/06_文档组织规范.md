# 文档组织规范

需求与 Task 及其显式引用的规范依赖，是目标、接口、行为和验收的唯一规范依据。源码、测试与运行结果用于观察实际实现是否符合文档，不能反向改变标准。

独立包根 README 是包级框架规范与文档组织入口，简洁维护稳定职责、边界、依赖、程序集和组合使用约定，不另建包根需求承接这些内容。仅在框架规范或文档组织规则变化时修改，不随新增功能维护能力清单、API 或执行状态。功能需求须显式引用适用的包 README 规范；Task 通过所引用需求继承这些约束，另行涉及的包规范须补充引用。具体功能仍由模块需求与 Task 规定。功能模块不另设 README 或替代说明层；项目根 README 与项目文档索引用于工作入口和导航，不能取代功能需求或 Task。

撰写时按读者目标组织必要内容，不机械填满模板或复述通用规范。需求聚焦目标、行为、边界、验收与待决，要求和验收可合并，并直接导航 Task，不承载动态进度；影响工作项的环境现状与执行记录归所属 Task。核查和区分事实不等于逐项写入正文。

## 可独立实施的文档

无论实现前后，任何 Agent 都应仅凭需求、Task 及其显式规范依赖取得完整的实现与验收规则，独立完成或重新完成实现、接通与验收。不得依赖本次源码、测试、会话或历史差异补齐关键规则；资源等实际输入可由文档定位，但不能代替行为说明。

- 需求明确可观察的行为、边界与验收结果；Task 落定影响实现的接口、状态与资源归属、执行顺序、失败终态及验证预期。已有规范契约可显式链接，包 README 提供框架约束，不能用实现说明或源码代替缺失的功能规则。
- 多个 Agent 可以依据同一版文档分别产出多套实现。文档约束共同目标与必要方案，未约定的普通代码细节由实现者决定，不把某套实现的选择自动提升为公共要求。
- Agent 在授权目标内解决常规工程选择，记录交接所需结论，不转为用户待确认问题。确有缺失的产品决定、重要公共契约变更或必需输入时，说明影响与解除条件；受影响部分不能宣称已可独立执行。

## 规范正文与执行记录

需求和 Task 的目标、方案、接口、行为及验收正文默认保持不变。执行及完成时只常规更新状态与结果；正文修订须满足[后续修改规则](#后续修改与当前结论)，不能从“执行任务”推导出用户另行授权修订正文。不得因实现完成、状态变为 `Done` 或代码既成事实而改写、压缩正文，用结果替换方案，或迁到实现说明中。精简、去重和整理不能作为执行中自行改正文的理由，也不能把正文换成源码、测试或实现说明的链接。

Task 唯一维护其执行状态、实际产物、当前前置缺口、验证结果、必要交接与下一步，放在与规范正文分开的执行记录与结果章节；更新记录不等于改变方案或验收要求。功能模块职责、边界、对外行为与用法归需求，接口约定、实施方案及相应示例归 Task；稳定的输入和就绪规则写在规范正文，当前是否满足写在执行记录。实际源码与测试入口由 Task 相关章节导航，不复制现状 API 为另一份契约。

## 目录与入口

根 [README](../../README.md)是项目工作入口，`AGENTS.md` 是 Agent 执行入口。项目级 `Docs/` 使用以下目录，根目录不放 Markdown 正文或重复 README：

- `Project/`：项目说明、使用指南与通用规范。采用连续两位数 `NN_名称.md`；新增接末尾，删除/合并后整理后续编号并更新入向链接，不预留空编号。编号仅用于阅读排序，按需读取。
- `Templates/`：需求与实施任务的填写结构，不使用 Project 的编号。

模块资料按[模块规范](08_模块组织与交付规范.md)放在模块根。既有资料变更位置前核查归属与引用，不自动迁移或删除。

## 创建、拆合与退役

| 情况 | 动作 |
|---|---|
| 可在当前会话完成的小修 | 沿用已有需求与 Task；实际文档问题先按后续修改规则讨论修正，执行结果可在会话或已有 PR 承接 |
| 长周期、跨会话或多人协作的真实需求 | 使用[需求模板](../Templates/需求文档.md)与[任务模板](../Templates/实施任务.md)，按模块规范就近建立需求与 Tasks |
| 已有模块继续迭代 | 回到原需求，续做范围相符的未完 Task；新增独立交付才就近拆 Task |
| 模块需要拆分 | 按模块规范确定边界，移动相关内容时修正引用 |
| 多份说明反复维护同一事实 | 不据此在执行中自行修改需求或 Task 正文；实际问题按后续修改规则处理，另有明确文档修订授权时按授权范围整理并保全必要语义与独立重新实现依据 |
| 模块需要工作入口或 API 接入说明 | 职责与对外用法写入需求，接口、方案与相应示例写入 Task；由需求直接导航 Task，不另建功能模块 README 或说明层 |
| 任务完成 | 保留规范正文，更新状态及必要结果；完成不代表需求或 Task 失去用途 |
| 用户取消或替代任务 | 在原任务写“已取消”或“已替代”，简记用户决定、交付范围及替代入口，保留必要依据和已有结果并退出活动导航，不以 Done 冒充交付 |
| 用户明确退役文档 | 按真实退役范围处理并修正引用；不根据 Done、无人引用或已有实现自行推断可删除 |

用户授权规划真实目标时，可建立 `NotStarted` Task，按上述标准写清实施方案及必要输入与依赖；也可仅讨论需求。不预填角色或结果占位，开工时明确实现者、评审者与唯一写入者。规划不等于实施授权，不为假想目标预造任务。文件名表达职责或具体交付，不带临时 Agent 名/状态；需要引用时才使用局部 AC 或 ID，已有 GF 标识可保留。

## 后续修改与当前结论

用户最新明确决定优先于尚未同步的旧文档，先回写必要规范再实施。项目规范规定共同规则，需求定义目标、行为与验收，Task 据此细化接口与实施方案；Task 不得擅自缩减需求。正文修订仅因有证据的实际问题启动，或由用户另行明确改变需求、授权文档修订；普通执行授权不包含为省事、精简或去重而修改正文。

执行前或过程中，若已确认的项目演进使旧假设或依赖失效，或条款自相矛盾、会导致 bug、确实无法实现等，应核实具体问题。项目现状与文档不符不等于文档有错；若属于实现偏差或尚未完成，应修正实现，不反向修改标准。

确认文档有实际问题后，先暂停依赖问题条款的实现，说明具体条款、事实依据、影响与修正建议，回到需求与 Task 讨论对齐；只修必要相关条款并同步关联规范，再依据修订版本继续。不受影响的部分可继续。常规纠错在已有授权内由主 Agent、实现 Agent 与独立评审讨论，不暗中改需求，也不增加逐次用户审批；尚未决定的产品或重要公共契约取舍仍由用户按[协作协议](04_Agent协作协议.md)决定。

用户改变需求或验收时，核对关联 Task 并更新受影响的规范依据；旧 Done 与历史结果不覆盖新要求。同一版文档供多套实现使用时，修正须明确影响哪些实现与验证结果，不能只适配其中一套。保留必要纠错说明即可，不另建历史副本或全局台账。

## 结果与保留边界

单次执行方法、结果、独立检查与限制简记在所属 Task 的执行记录与结果章节；已授权小修可在会话或已有 PR 承接，不机械新增文档。状态按[Task 分工](08_模块组织与交付规范.md#3-task-分工与交付状态)对应具体实现与执行维护，不相互覆盖或代用，不另建文档台账。长期回归保留测试源码、配置与可重现命令，运行日志和 XML 留工具临时输出或 CI；这些结果不替代规范正文。

不创建独立 Evidence、验证 README、测试/发布报告、来源哈希、历史归档或变相副本，也不把原始输出全文搬进既有正文。发布、疑难问题与文档整理使用同一规则；清理报告不删除测试源码和命令。外部项目仅供参考，适用结论写入当前规则，不复制来源文档或生成阅读记录、治理流水与全局台账。

# 模块组织与交付规范

模块应有清楚的边界、工作入口、当前状态和交付责任。协作执行[协作协议](04_Agent协作协议.md)，质量与验收执行[工程标准](05_工程实施与验收标准.md)，文档拆合原则与维护纪律执行[文档组织规范](06_文档组织规范.md)。

## 1. 模块边界与根

- 按独立职责、契约、生命周期或验收边界划分模块并指定负责人；文档按[稳定功能边界](06_文档组织规范.md#按功能边界组织文档)组织，共有规则不互抄，文档拆分不强制改变代码目录。
- 项目系统的模块根按[项目架构](02_架构与模块.md)确定，`Assets/Game/<模块>/` 仅为默认位置；用户已指定的目录优先，不得按默认规则自动迁移。包内能力以所属能力目录为模块根，独立包以仓库根为入口；模块不等同于独立仓库、包或程序集。
- 跨包实现保留在正确层，由主责模块链接权威契约与适配入口，不为模块内聚迁移或复制其他层的实现。
- 项目级资料只维护总体目标、共同规范、模块入口与真正项目级集成；项目模块沿 02 发现，包内能力按包 README 的目录约定定位模块根，不要求全部子模块登记到全局或包 README。

## 2. 入口与工作资料

独立包根 README 简洁维护稳定的框架职责、边界、依赖、程序集、组合使用与文档组织约定；只有这些规则变化时修改，不随功能扩展登记能力或状态，也不另建包根需求或功能索引。

功能模块根就近组织资料，新建默认结构如下；按实际需要保留内容，不创建空文档或空目录，不另设功能模块 README：

```text
<模块根>/
  Docs/
    需求与实施.md
  <所属代码、资源与测试>
```

- `Docs/需求与实施.md` 同时承载需求、必要设计、实施工作项、验证预期与分开的执行记录。适合按独立功能拆分时，在同一 `Docs/` 下使用 `<独立功能名称>.md`，每份均明确自身目标、范围与完整实施验收依据；真实子模块也可在自身根使用默认结构。
- 先从已有上层入口或包目录约定定位模块根，再查看该模块 `Docs/` 下的功能文档，按标题与范围选择本次功能，继续读取其直接依赖。子模块通过已有父级导航或模块目录发现。只有父模块确有共有规范或联合交付内容时，才保留相应父级功能文档并链接子功能；不为列文件另造纯导航文档。
- 功能文档显式引用适用包 README 及其他规范依赖，工作项就近引用相关契约章节。跨文档依赖直接链接权威定义，按需使用稳定章节标题定位具体契约或工作项，不复制依赖正文和进度。
- 按[可独立实施标准](06_文档组织规范.md#可独立实施的文档)组织接口、状态机、必要方案及验证方法与预期，接口和验收所需示例就近放入对应章节。未实现时不将规划能力或示例冒充已交付事实；实际源码和测试入口用于定位产物，不另写一套现状 API 文档作为契约。
- 复制模板时修正相对链接，独立包须显式定位其规范依赖，不能删除独立实施必需的规则。既有 `Docs/需求.md + Docs/Tasks/` 未迁移时，仍从需求直接导航 Task 并沿用原有职责；是否迁移按[渐进调整规则](06_文档组织规范.md#既有文档的渐进调整)处理。

## 3. 工作项分工与交付状态

- 工作项（Task）按实际交付组织，写明产物与消费者、规范章节、必要输入与依赖、验证责任。一个功能文档可以有多个工作项，分别推进和验收；多个工作项本身不构成拆文档理由。单项可简化结构，不要求额外编号或表格。
- 每个工作项按具体实现与执行分别维护 `NotStarted / InProgress / Blocked / Done`，状态、实际产物、当前前置缺口及影响、验证结果、必要交接与下一步只在所属执行记录中维护一次。多套实现分别记录，不相互覆盖或代用；头部或其他位置需要导航时引用记录，不重复保存状态。取消或替代时保留原因、交付范围与替代入口。
- 需求或交付范围、关键阻塞、集成或验收结论变化时，更新受影响工作项的相应记录；规范正文的变更遵守文档维护规则，不因查询或会话生成状态快照。既有单套 Task 文件可继续在头部唯一维护状态。
- 消费方在自身工作项记录所需输入、当前依赖缺口及其影响，提供方状态通过引用其对应工作项查询；按所需产物的实际就绪条件判断是否能开始，不等待提供方整个模块 Done。
- 不另设状态或汇总文档，不预造只有汇总用途的工作项。有真实联合交付时，由实际承担集成的工作项承接；各子项 Done 不能代替联合验收。

## 4. 提供与依赖契约

- 同时明确本模块提供什么、需要什么；按实际边界说明契约负责人、实现方与消费方、数据与生命周期、就绪、失败、兼容及可判定条件。
- 已有契约直接引用功能文档或其显式规范依赖中的定义；既有结构引用需求或 Task 的权威章节。通用契约与项目专属实现遵循架构归属，不为尚未成立的需求预造接口或扩展机制。

## 5. 推进与验收

- 开工前从功能文档确认目标与边界、必要输入及就绪条件、工作项依赖顺序、唯一写入范围和验证入口与判据。同一文档由一个写入者维护；条件未满足时按协作协议推进可独立部分，不掩盖缺口。
- 跨模块工作涉及联合交付时须明确最终集成者。有自然业务归属时，由主责模块持有联合需求与验收，其他模块的工作项引用；真正项目级集成才由项目层承接。实际集成工作项引用提供方的对应工作项及契约，不抄写状态；各子项对应实现为 Done 不等于约定的模块联合验收完成。
- 按工程标准验证真实交付，不能用替身或局部测试冒充真实集成。必要验证与最终独立检查均满足后，才能将对应工作项及实现标为 Done；必要 Unity 验证未执行时注明“待用户验证”。具体分工、条件验证与有效豁免按协作协议执行。
- 交付后在所属工作项记录必要结果，正文仍足以独立重新实现。实际文档问题先讨论修正，修订条件及用户另行授权按[后续修改规则](06_文档组织规范.md#后续修改与当前结论)处理，不因实现完成改正文。
